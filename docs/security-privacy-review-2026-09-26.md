# Security and employee privacy review — 26 September 2026

This review covers the Flask application and the requested security/GDPR checklist. It describes implemented controls and work the employer must complete. A preview deployment is **not** proof of GDPR compliance or production readiness.

## Applied in the application

| Area | State |
| --- | --- |
| Passwords | Werkzeug `scrypt` hashes; no plaintext password storage. Minimum eight characters; login is rate limited and uses a generic error. Unknown accounts also run a dummy password verification to reduce timing differences. |
| Sessions | Signed Flask cookie, Secure on Vercel/production, HttpOnly, SameSite=Lax, 12-hour lifetime. Login clears prior session and CSRF token. Password changes invalidate existing sessions by binding the session to the current password hash. There is no server-side session ID to regenerate. |
| CSRF | Existing central token validation covers all unsafe methods and accepts `X-CSRFToken` for AJAX. This is a custom equivalent; Flask-WTF is not installed. |
| XSS/SQL | Jinja escaping remains enabled; no `|safe` or raw SQL string interpolation found in this code review. CSP restricts scripts to self plus a per-response nonce; inline style attributes were removed. |
| Requests/uploads | In-process per-IP limits for traffic, writes and login; bounded memory; HTTP 429 with Retry-After. Uploads are size, extension, MIME/signature and pixel checked; Excel files have compressed/uncompressed/row/column limits. |
| Headers | CSP, HSTS on secure deployments, `nosniff`, `DENY` frame policy, referrer policy, private no-store for dynamic pages. TLS and HTTP redirect are supplied by Vercel for Vercel domains. |
| People | Admin sees all profiles; project manager sees own profile and direct reports; other roles see only own profile. Employee directory and search use the same scope. Operational screens still display the names of relevant colleagues for requests and asset history, without links to unrelated private profiles. |
| Data rights | Authenticated employees can inspect/edit their profile and export an account-data JSON. A full Article 15 request for historical/free-text data still needs human review. Admin can deactivate and remove identifying fields from an inactive profile; historical attribution keeps a pseudonymous ID. This is not complete erasure. Existing delete is also available to admin. |
| Audit | Login failures, denials, profile views/changes, role/status changes, export, anonymization and password changes are logged by actor/target IDs. Email/password/token values are not included in these events. Vercel controls retention and integrity of production log streams; this is not a database-backed tamper-proof audit trail. |
| Dependencies | `requirements.txt` uses exact versions. `pip-audit` found two advisories in `anyio==4.13.0`; upgraded to `4.14.2` and re-audited with no known findings. `npm audit` also reported zero findings. |

## Required owner and infrastructure decisions before production promotion

1. **Set an employee data policy.** Identify the legal controller (exact company), privacy contact, purposes and lawful basis per data category, retention periods and access-request channel. Have counsel or the data protection lead approve the internal notice. The `/privacy` page deliberately does not invent those facts.
2. **Record retention.** Decide periods for active/inactive employee profiles, transfer history, service records, uploaded invoices, application logs and backups. Record exceptions for legal claims/accounting. The current user table has no deactivation timestamp; there is no safe automatic purge without a schema/operational change. Perform a documented periodic review in the meantime. Anonymization does not erase personal names manually typed in free-text notes, prior exports, backups or public upload URLs.
3. **Storage privacy.** `supabase/storage.sql` defines the existing bucket as public. Images and service invoice URLs may be accessible to anyone holding a URL. Plan a private-bucket migration, authenticated serving, URL migration and rollback; do not flip the bucket in place while the application still uses public URLs. Review legacy local uploads under `public/static/uploads` as well. This is the main unresolved confidentiality issue.
4. **Distributed abuse protection.** In-process rate limits are per Vercel instance and cannot stop a distributed flood. In Vercel Firewall, create a rate limit for login and/or unsafe methods per IP, start with logging, inspect real traffic, then publish a blocking action with appropriate thresholds. Review plan limits and cost. Only the account owner can apply this infrastructure setting.
5. **Supplier controls.** Check the actual agreements and applicable Data Processing Addenda with Vercel and Supabase and document hosting regions, subprocessors, international transfers, access controls, database/storage encryption at rest, backups and incident contacts. Do not assume that a public URL is encrypted access control.
6. **Breach response.** Record discovery time, scope, affected data, containment, evidence and contact person. Assess risk promptly. If Article 33 notification is required, notify the Bulgarian CPDP without undue delay and, where feasible, within 72 hours after becoming aware; assess Article 34 communication to affected people when high risk. Preserve the incident register even where notification is not required.
7. **Monitoring.** The application records assigned construction sites and manual movements of equipment. It does not ingest continuous worker GPS trails. If telemetry is added later, reassess necessity/proportionality, provide prior employee information and consider a DPIA before enabling it.
8. **2FA.** No 2FA is implemented. Evaluate adding it for administrator accounts through a separately designed authentication change, including recovery and account migration.
9. **Access policy for equipment.** The existing workflow intentionally allows all authenticated roles to see equipment and locations across sites and to request movements. Restricting equipment to an assigned site would change that workflow; agree the operational scope and test request flows before doing so.
10. **Secret scan and dependency audit.** Run a dedicated `gitleaks` scan of all Git refs and `pip-audit -r requirements.txt` in CI before each production release. `pip-audit` was run here; `gitleaks` was not available. Review findings without printing secret values; rotate any exposed key immediately. Verify Vercel `DEBUG=False`, HTTPS and production environment variables in dashboard.
